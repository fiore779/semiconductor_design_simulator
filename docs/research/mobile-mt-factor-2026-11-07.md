# スマホ SoC の MT 持続クロック係数を 0.81 → 0.92 に再校正(2026-11-07)

ユーザー指示: 「NG になっているものも修正して」。NG の大半が Arm スマホ SoC の MT だったため、`js/sim/perf.js` の `MT_CLOCK_FACTOR.mobile` を 0.81 → 0.92 にした。**mobile-pc の 0.81(電力未取得のフォールバック)と TDP 帯係数 0.69 / 0.76 は変えていない**。ユーザーが指示したのは「NG を直す」ことで、0.92 にするか・世代別に分けるかは実装上の判断である。

## 1. 根拠

`kind==='mobile'` で MT が計算でき、公開値(GB7 マルチ)がある 18 件(qc-855/865/888/8gen1/8plus-gen1/8gen2/8elite/8elite-gen5/8elite-x-gen6/780g/7gen1/7gen3/720g/6gen1/4gen2、mt-9000/9200/8200)について、予測が公開値と一致する係数を二分法で逆算した。中央値は **0.925**(範囲 0.629〜1.292)。丸めて 0.92 にした。

注意:
- **チャート値からの逆算で、チャートの偏りを含む。[推測・未検証]**。熱・電力制限を表すものではない。
- 係数は世代でばらつく(8 Elite 系は 0.63〜0.76、古い 855 / 865 / 888 / 720G は 1.1〜1.3)ので、1 つの係数では表せない。残る NG は世代差で、原因は未特定。推測で個別に合わせていない。
- 前提となる校正(Arm の u、各 SoC の l3MB)は `docs/research/slc-as-l3-2026-11-07.md` の状態。

## 3. 判定の反転

- **MT の ng → ok(8 件)**: qc-8gen1、qc-8gen2、qc-780g、qc-4gen2、qc-6gen1、mt-9000、mt-9200、mt-8200。
- **MT の ok → ng(2 件)**: qc-8elite-x-gen6(+5.5% → +17.1%)、qc-7gen1(-2.3% → +10.3%)。係数が上がって、必要係数が 0.92 より低い SKU が過大側に動いた。
- ST・x86・Apple・NVIDIA・mobile-pc の数値は不変(変わったのは kind:mobile の MT 18 件のみ)。

## 4. 残る NG(MT、9 件)

qc-855(-24%)、qc-865(-20%)、qc-888(-13%)、qc-8plus-gen1(-10.1%)、qc-8elite(+33%)、qc-8elite-gen5(+38%)、qc-7gen1(+10.3%)、qc-720g(-18%)、qc-8elite-x-gen6(+17%)。いずれも係数では直らない世代差(古い世代は必要係数が高く、Oryon 系は低い)で、原因は未特定。推測では合わせない。ST の ±10% 外(A14 +10.6%、780G -13.8%、7+ Gen 3 +12.6%、720G ほか)は今回触っていない。

## 5. 変更したもの

- `js/sim/perf.js`: `MT_CLOCK_FACTOR = { pc: 1.0, mobile: 0.92, 'mobile-pc': 0.81 }` とコメント(根拠・日付・「チャート値からの逆算で偏りを含む。推測・未検証」)。
- UI の注記(`js/ui/results.js`)は、スマホ SoC の係数を数値で固定記述しておらず、そのまま実際の係数を表示するので変更なし。
- テスト: `perf.test.js` の mobile 係数テスト、`mix.test.js` の BASE(12 件)・BASE_M5B(6 件)、`memory-baseline.json`、評価ハッシュ。

### 直したもの(原因が分かって直した)

- Zen+ が ISA 平均 u を使っていた → Zen 1 の u を借りる(uFrom)。
- Zen 3 に校正代表がなく ISA 平均 u を使っていた → 5800X を代表に(σ の代表にも入る)。
- Oryon Performance の u が無く ISA 平均に落ちていた → Oryon Prime の u を借りる。
- A76 / A77 / X1(855・865・888)に代表がなかった → 代表にした(Android の機種中央値 n が多い)。
- A78 の u が ISA 平均だった → 4 件の中央値の uCal。
- Arrow Lake の L3 遅延が実測より小さかった → 実測値 [二次]。

### 直せないもの(データ待ち・判断待ち)

1. モバイル x86 の ST +13〜32%: 主因は公開値側(チャートは全投稿の平均で、省電力の投稿に引き下げられる)。Notebookcheck のレビュー機と比べると 14700HX -0.3%、7840HS +0.2%、275HX -3.9%。取り直しが必要(Geekbench Browser は 403)。
2. 5950X の MT +23%: 全コアクロック(PPT 142W を 16 コアで分けると約 3.85〜4.0GHz、boost の 0.8 倍。HEXUS/KitGuru [二次])が要因。任意項目 allCoreGHz の追加と σ の代表の全コアクロックの揃えが必要。
3. Arrow Lake の残り +11〜15%: 原因未特定(SMT なしの η、ダイ間遅延の疑い)。
4. モバイル x86 の MT 帯係数: 合わせ込みの限界(HX 370 は Zen 5c に係数を掛けないと +0.2% だが、出典なしで推測)。
5. 8 Elite 系の MT: 電力制約(k ≈ 0.75〜0.78)でコア電力のデータ待ち。
6. 8 Elite Extreme Gen 6 の ST -28%: 公開値の出所の差(直近 25 件は Honor 多めで GB7/GB6 = 0.77、Gen 5 のチャートは 0.55)。P の 6 コアは実際は 4.03×3 + 3.74×3 GHz。
7. Dimensity 9400 と GB10 の差: Android の GB7 の出所による(GB7/GB6 が高い群 0.84・低い群 0.48 の混在)。nv-gb10 を calib:false に戻す案もある(9400 ST 0%、GB10 -26% / -18%)。
8. L3/SLC 未定義の 780G・6 Gen 1・4 Gen 2・7 Gen 1・7 Gen 3・720G・Dimensity 8200: 容量が取れていない(780G は 2MB / 3MB で割れ、公式値なし)。
9. 4 Gen 2 の GB7 は 2 系統で食い違う(771 / 1855 と 916 / 3469)。
10. A77(865)の代表は、A77 を持つ SKU が 1 件(GB7 の n=14)で検証用の SKU がない。
