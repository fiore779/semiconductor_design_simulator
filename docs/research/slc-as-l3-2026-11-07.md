# SLC 全体を L3 相当として cfg.l3MB に入れた影響(2026-11-07)

ユーザー指示(2026-11-07): 「現在は GPU の機能は未実装なので、SLC 全体を使えるようにしてください」。設計書 §5.3.0「L3 容量の取得と反映」の旧方針(Apple・Qualcomm・MediaTek の SoC は SLC が別階層なので cfg.l3MB を未定義にする)を変更し、**GPU 未実装の間は SLC 全体を CPU が使える最終段キャッシュ(L3 相当)とみなして cfg.l3MB に入れる**。

狙い: l3MB が未定義だと `js/sim/perf.js` は参照値 l3Ref = 2048KB をスレッド数で割らずに使うため、MT が楽観側(スレッドあたり 2MB 扱い)になっていた。それを解消する。

## 1. 入れた値(既存の notes / docs/research に記録済みのものだけ。新しい推測なし)

実装は `data/presets/chips-soc.js` 末尾の表 `SLC_AS_L3`。cfg.l3MB のほか cfg.l3Note に「(内訳)の合計 N MB([区分])。SLC 全体を L3 相当として使用(GPU 未実装のため。2026-11-07 ユーザー指示)」を書いた。各プリセットの notes にも同趣旨の文を入れ、旧文言「SLC は別階層のため l3MB には入れない」はすべて直した。

**入れなかったもの(null のまま。合計が分からない)**: Apple A17 Pro(`apple-uarch.md` §2.4 の SLC が空欄で A16 と結合の可能性)・M4 Pro(未取得)、Snapdragon 8s Gen 3(L3 が 8MB と 12MB で割れる)・8s Gen 4・7+ Gen 3・7 Gen 1/3/4・720G(SLC 1MB のみ)・780G・6 Gen 1・4 Gen 2、Dimensity 8200(L3 4MB のみで SLC 未取得)。NVIDIA は §7b のとおり Orin(6→10MB)・GB10(24→40MB)に記録済みの SLC 相当を足した(T239 4MB・Thor 16MB は SLC 未取得で従来どおり)。

L3 が null のプリセットは 53 件 → 13 件(Apple 2・Qualcomm 10・MediaTek 1。8 Gen 3 は追補で 12MB を入れた)。

## 2. 影響の確認方法

変更前後の `evaluate(fromPreset(p))` を全 102 プリセットで比較(変更前は `data/presets/chips-soc.js` の元ファイルで計算)。判定は ±10%(`evaluate.js` の TOLERANCE)。x86(Intel・AMD)の ST/MT は 1 件も動かない。電力・温度は SoC では計算不能(null)のままで、変化なし。

## 3. 校正が動いた(重要)

当初の想定は「SoC は mobile-pc の x86 だけが校正の対象なので動かない」だったが、**Arm の校正の代表 SKU(M1・M2・A16・8 Gen 1・8 Gen 2・8 Elite・Dimensity 9400)にも l3MB が入った**ため、`calibrate`(代表 1 件で u を決める)の結果が動いた。代表は GB7 の公開値に合わせる(ST は代表自身では誤差 0 のまま)ので、L3 を入れた分だけ u が下がった。

その結果、**l3MB を入れていない Arm SoC(780G・7 Gen 1/3・720G・6 Gen 1・4 Gen 2・8 Gen 3 は代表なので不変)や、専用 u を借りる A17 Pro・Orin・T239・GB10 の ST/MT も動いた**(ISA 平均 u や借用元の u が下がったため)。特に A17 Pro は Everest の u を借りており ST が 2824.8 → 2457.8(+11.8% → -2.7%)に大きく動いた。GB10 は X925 の u 低下で ST -18.5% → -26.9%、MT -13.1% → -21.5% になり、さらに GB10 自身の l3MB を 40 にして最終的に -26.0% / -18.0%(どちらも ng のまま、悪化。§7b)。

これは設計どおりの連鎖だが、「l3MB を入れる = 校正の代表の u が下がり、同じ ISA の他 SKU も下がる」という副作用があるため、受け入れるかは判断待ちとして設計書 §13.4 に記録した(ユーザーが決めたのは「SLC 全体を使う」方針だけで、この連鎖の影響の受け入れではない)。

**基準の混在**: l3MB が未定義の Arm SoC(8 Gen 3 とその u を使う SKU、780G・7 Gen 系・6 Gen 1・4 Gen 2 ほか)は、L3 を参照値 2MB で計算するのに、ISA 平均 u や借用 u は L3 を持つ代表で下がった値を使う組合せになる。8 Gen 3 の記録済み L3 12MB を入れるか(SLC 未取得で合計は不明)も判断待ち。

## 6. 判定の反転まとめ

- **MT の ok → ng(7 件)**: qc-888(-9.4%→-21.5%)、qc-8gen1(-1.4%→-11.1%)、qc-8gen2(-1.2%→-10.6%)、mt-9000(-9.6%→-17.6%)、mt-9200(-6.9%→-15.3%)、mt-8200(-2.2%→-10.3%)、qc-4gen2(-2.1%→-10.3%)。MT が楽観側だった見かけの ok が外れた(Orin で 2026-11-05 に起きたのと同じ型)。8 Gen 1 / 8 Gen 2 は校正の代表(ST は代表)だが MT の代表ではない。
- **MT の ng → ok(1 件)**: qc-8elite-x-gen6(+21.3%→+5.9%)。
- **ST の ok → ng(3 件)**: apple-a14(+8.4%→+10.6%。A14 は L3 を入れて悪化)、qc-780g(-5.5%→-13.4%)、qc-6gen1(-9.3%→-16.9%)。780G・6 Gen 1 は l3MB を入れておらず ISA 平均 u の低下による。
- **ST の ng → ok(2 件)**: apple-a17pro(+11.8%→-2.7%。ただし借用 u が下がって打ち消し合っただけで原因が解消したわけではない。notes の errCause に追記)、mt-9300(-11.2%→-0.9%)。**mt-9300 の ok は、代表の 8 Gen 3 が l3MB 未定義(参照値 2MB で校正)なのに 9300 は 18MB で計算している、という基準の混在による見かけの改善**で、モデルが良くなったわけではない。同じ混在は l3MB が null の Arm SoC(780G・7 Gen 系・6 Gen 1・4 Gen 2 ほか。L3 を持つ代表で下がった u と参照 2MB の組合せ)全般にある。
- MT の縁: qc-780g は -9.95%(ok のまま、限界)、mt-8200 は -10.32%、qc-4gen2 は -10.25%(ng)。

## 7. その他の副作用と対応

- **フロアプラン**: Apple・Snapdragon・Dimensity は写真の枠に L3 の置き場所が無い(飾りの SLC のみ)ため、L3 ブロックは増えない。`floorplan.js` の `afterEdit` は、元は「l3MB > 0 なら schematic に落とす」だったが、そのままだと元から l3MB を持つ Apple の全編集が schematic になるため、**元の容量(baseCfg.l3MB)から変えたときだけ**落とすよう第 4 引数を足した(`design.js` の `relayoutCompute` が baseCfg を渡す)。写真なしの従来配置(M5 Max・8+ Gen 1)は L3 ブロックが 1 つ出る。
- **部品ライブラリ**: SoC の L3 の部品(推定面積)が 37 件増えた(178 → 215。M5b 追加分を除く)。
- **テスト**: `mix.test.js` の BASE(24 件)・BASE_M5B(8 件)、`tests/fixtures/memory-baseline.json`(33 件)、`floorplan-scale.test.js` の評価ハッシュ、`floorplan-snapdragon.test.js` のブロックのハッシュ(M5 Max・8+ Gen 1 を除く 67 件)、`perf.test.js`(mt-9300 を外れ値から検証ペアへ)、GB10・A17 Pro・floorplan 系・evaluate の校正範囲(L3 なしの例を M4 Pro に)を更新。

## 7b. NVIDIA(レビュー対応で追加)

ユーザー指示は「SLC 全体を使う」なので、記録のある SLC 相当を NVIDIA にも足した。
- Orin: 6 → 10MB(L3 6MB〔公表〕+ System Cache 4MB。旧記録は L4 扱いで notes のみ)。ST 722.2 → 737.5(-8.6% → -6.6%、ok のまま)、MT 5432.6 → 5769.8(-21.1% → -16.2%、ng のまま)。2026-11-05 の l3MB 6 の時点は ST 788.0(-0.3%)・MT 5927.0(-13.9%)。
- GB10: 24 → 40MB(L3 24MB〔公表〕+ SLC 16MB〔[二次] `nvidia-gb10.md`〕)。ST 1918.3 → 1941.0(-26.9% → -26.0%)、MT 16170.0 → 16884.4(-21.5% → -18.0%)。両方 ng のまま。変更前(SLC 反映前)は ST 2137.5(-18.5%)・MT 17890.6(-13.1%)。写真の L3 枠(16 + 8MB)は frame の `l3Frac` 0.6 で cfg の 24/40 を表し、SLC は飾りのまま。
- T239(4MB)・Thor(16MB)は SLC 未取得で従来どおり。判定の反転はこの 2 件にはない。

## 7c. 旧保存データの補正

変更前に保存した設計は cfg.l3MB=0 / baseCfg.l3MB=0 で保存されており、そのままだと「L3 なし」で評価される。`design.js` の `parse`・`ensureCfg` で、プリセットの l3MB>0 なのに baseCfg.l3MB===0 のものを旧データとみなして baseCfg.l3MB(cfg.l3MB も 0 のままなら同じ値)をプリセットの値に直す。ユーザーが L3 を 0 にした設計(cfg=0、baseCfg=プリセットの値)は直さない(Orin の null→6→10 も同じ型)。

## 7d. 追補: 8 Gen 3 の L3 12MB と GB10 を X925 の 2 件目の代表に(直前のコミット 65e7528 との差)

ユーザー指示「GB10 の測定だけ低すぎるのでそれだけ修正したら確定。8 Gen 3 の L3 キャッシュも入れて」。GB10 の直し方はユーザーが選択肢から「X925 の校正に GB10 も加える」を選んだ。

変更点:
- **8 Gen 3 に l3MB 12**(`SLC_AS_L3` に追加。L3 のみで SLC は未取得なので SLC は含まない。Android Authority・ComputerBase の値で、Notebookcheck は 8MB と食い違う)。これで「l3MB 未定義の代表」だった 8 Gen 3 の基準の混在は解消した(§13.4 の混在の行から 8 Gen 3 を除いた)。
- **GB10 を Cortex-X925 の 2 件目の校正代表にした**(`reps` に nv-gb10。calib:true。addedIn は M5b のまま。`tools/validate-data.js` は「追加分の calib は false」に GB10 だけ例外を設けた)。X925 の u は Dimensity 9400 と GB10 の 2 件の中央値(= 平均)。

### 判定の反転(65e7528 → 今回)

- **ST の ok → ng**: mt-9300(-0.9% → -10.2%。8 Gen 3 に L3 12MB を入れて X4 の u が下がったため。§6 で「基準の混在による見かけの改善」と書いたものが解消し、予告した値と一致)、mt-9400(代表だった 0% が +17.6% に。X925 の u が 2 件の中央値になり、9400 自身は 0% にならないため)。
- **MT の ok → ng**: qc-780g(-10.0% → -10.4%。縁だった ok が外れた)。
- **MT の ng → ok**: nv-gb10(-18.0% → -8.6%)。
- **GB10 の ST は -13.0% でまだ ng**。理由はプラットフォーム差の疑い: GB10 の Geekbench 7 は Linux 上の測定で、Dimensity 9400(Android)より約 40% 高い値が出ており、同じ X925 の u 1 つでは両方を同時に合わせられない(2 件の中央値にしたので 9400 が +17.6%、GB10 が -13.0%)。原因が OS・電力・メモリ構成のどれかは未特定。
- 上記以外の SKU は判定の反転なし。
