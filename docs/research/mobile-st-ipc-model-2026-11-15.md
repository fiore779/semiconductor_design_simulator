# モバイル x86 の ST 過大を IPC 項で説明・計算する方法(2026-11-15)

- 依頼: 「モバイル x86 の ST に一律 ×0.90 を掛けるのではなく、IPC で計算するようにして」。一律の係数を使わずに、モデルの IPC 項(キャッシュ・メモリ遅延・コア間接続・クロック依存)の差として、出典付きで説明し計算する方法を設計する。
- 対象の状態: 作業ツリー(HEAD f6ce6c3「265K の P コアの boost を ARK の Max Turbo 5.5GHz にする(C1)」の後)。全 158 判定のうち ng は 13 件。σ=0.03183、x86 の ISA 平均 u=109.39、Zen 3 105.73、Zen 4 131.48、Zen 5 113.70、Lion Cove 100.36、Golden/Raptor uCal 116.5、Cougar Cove uCal 98.3、Redwood Cove uCal 99.5、Cezanne は Zen 3 × 0.95。
- **コード・データ・設計書は変更していない(調査と試算のみ)**。試算は `js/sim/perf.js` をスクラッチパッドにコピーし(`perf_hook.js`)、`stScore` の中で SKU ごとに `dramNs`・uarch の値・ST の L3 を差し替えるフックを足して行った。読み込みは `tests/evaluate.test.js` の `ev()` と同じ(`tests/helpers.js` → `E.makeContext()` → `E.evaluate(design.fromPreset(p), ctx)`)。フックが無いときは現状の評価と一致することを確認した(S0)。スクリプトはスクラッチパッドの `perf_hook.js`・`exp.js`・`lat.js`・`main.js`・`drop.js`。
- 区分: [実測] = 測定値(Geekbench Browser の投稿、レビューの測定)、[公表] = メーカーの原ページ、[二次] = レビュー・解説記事の記述(Chips and Cheese の測定値も、記事経由なので [二次] とした)、[推定] = 本メモの計算・代用、未取得 = 取れなかったもの。取得日は特記なければ 2026-11-15。

## 0. 結論(要約)

1. **モデルの IPC 項は、今はモバイルとデスクトップで「L3 容量」しか変えていない**。DRAM 遅延は全 SKU で 85ns 固定。`memory.js` の種別遅延表(DDR4 76 / DDR5 90 / LPDDR5 125 / LPDDR5X 120)は「選んだ構成 ÷ 基準構成」の比でしか使わないので、プリセット(基準構成)の ST には効かない。L2・L3 の遅延は uarch ごとの値で、Lunar Lake にも Arrow Lake(デスクトップ)の値が入っている。
2. **IPC で説明できるのは主に DRAM 遅延の差で、量は 0〜-3.8%**。出典のある実測遅延(デスクトップ 70〜99ns、モバイル 103〜148ns)を各 SKU の `dramNs` に入れ、u と uCal を同じモデルで取り直すと、モバイル x86 の ST の中央値は +7.6% → **+4.9%**、MAE は 7.07 → **5.63**。ST の ng はモバイルで 6 → 4 件(Kraken 350 +14.5 → +9.6、7840HS +10.4 → +8.8 が ok)。デスクトップの ST は ±0.5 ポイント以内しか動かない。
3. **分布の上側(P90)の機体と比べると、IPC 項を入れた後のモデルの残りはほぼ 0 になる**(予測 ÷ P90: HX 370 +4.6 → +0.6%、350 +4.2 → -0.2%、7840HS +2.5 → +1.0%、7735HS +5.1 → +2.3%、285H +5.6 → +2.6%、268V -2.1 → -4.7%)。**IPC 項で説明できるのは「モデルと最良条件の機体との差」で、「最良条件と Windows 投稿の中央値との差」(+7〜+12%)は IPC ではない**。後者は投稿機のクロック(電源プラン・OEM の電力設定)の差で、5800U では投稿の 72% が最大ブーストに届いていないことが結果ページから確認されている(`5800u-st-cause-2026-11-14.md`)。
4. **推奨(実装はユーザー判断)**: (A) プリセットに「プラットフォームの DRAM 遅延 [ns]」(出典・区分つき)を持たせ、`stScore` の `dramNs` をその値にする(ST だけ。未取得は 85ns のまま)。(B) 同時に Golden/Raptor・Cougar Cove・Redwood Cove の uCal を同じモデルで計算し直す。(C) MT への反映は、連続式の c の再校正と一緒に別に行う。Lunar Lake の L2 2.5MB・L3 51 サイクルと HX 370 の ST の L3 16MB は、事実なので (A) と一緒に入れてよい(LNL は +1.7 ポイント上がる向き)。
5. **直せない残り**: 285H +11.5%、5800U +14.4%、14700HX +11.1%、7735HS +10.6% は ng のまま。5800U と Raptor の HX は DRAM 遅延の出典が無い(未取得)。これらの残りは、投稿の母集団(実クロック)の差で、IPC 項では説明できない。公開値に合わせる係数は作らない。

## 1. 現在の ipc_model がモバイルとデスクトップで変えているもの(確認済み)

`coreCpi`(perf.js 28〜67 行)の式は CPI = 1/min(W, 0.55·ROB^0.5) + 分岐 + メモリ。メモリ = (m1·L2遅延 + m2·L3遅延 + m3·dramNs·f) / MLP。

| 項目 | モデルでの扱い | モバイルとデスクトップで違うか |
|---|---|---|
| L1・L2 の容量 | uarch.js の `l1dKB`・`l2KB` | 同じ uarch なら同じ(LNL の L2 2.5MB も ARL の 3MB で計算) |
| L2・L3 の遅延 | uarch.js の `l2Lat`・`l3Lat`(サイクル) | 同じ uarch なら同じ。Lion Cove は ARL デスクトップの 84 サイクルで、LNL(51 サイクル [二次])にも使っている |
| L3 の容量 | `cfg.l3MB`(ST は 1 CCD 分) | **違う(唯一の差)**。5800U・7735HS・7840HS・350 は 16MB、デスクトップ兄弟は 32MB |
| DRAM の遅延 | `dramNs: 85`(全 SKU 共通)× f | **違わない**。`memory.js` の `dramScale` は基準構成なら 1 |
| メモリ種別 | `cfg.memory` の文字列は ST に使われない。`data/memory.js` の基準構成は比の分母にだけ使う | 違わない |
| コア間接続(リング・CCX) | 無い(L3 遅延のサイクル数に含まれるだけ) | 違わない |
| クロック依存 | DRAM 遅延だけが f に比例(f が高いほど IPC が下がる) | 同じ式。モバイルは f が低めなので、同じ遅延ならむしろ IPC は少し高い |

現状のメモリ項の CPI(`parts.mem`)は、モバイルとデスクトップ兄弟でほとんど同じ: Zen 4 7840HS 0.0649 / 7700 0.0595(差は L3 16MB 対 32MB だけ)、Zen 5 350 0.0438 / 9700X 0.0406、Lion Cove 268V 0.0311 / 265K 0.0272。

- **L3 の容量はすでにモデルに入っていて、モバイルの過大の原因にならない**(デスクトップでも L3 の小さい 2200G・2400G・12100 は過大側でない。`mobile-st-cause-2026-11-13.md` §2.1)。L3 の遅延は、測定のあるモバイル(Phoenix・LNL)ではデスクトップと同じか短い。**コア・L3 間の接続で ST が下がるという出典は見つからなかった**(Strix Point のクラスタ間の遅さは、ST の 1 スレッドには効かない)。

### 2.3 ST 実行中のクロック(IPC ではない)

- 5800U: Windows 投稿 76 件の Maximum Frequency の中央値は 4064MHz で、4.4GHz 以上は 21 件(28%)だけ。4.4GHz 以上の投稿の ST 中央値は 1823 で、全体の中央値 1614 より +13.0% [実測](`5800u-st-cause-2026-11-14.md` §1.1)。
- 7840HS: Chips and Cheese の HP の機体は「最大 4.5GHz に制限(本来は 5.1GHz)」、ROG Ally は 5.1GHz まで上がる [二次](§2.1 の Phoenix の記事)。**同じ SKU でも機体の設定で ST のクロックが 1 割以上違う**ことの直接の例。
- 分布: モバイルの ST の P90 ÷ 中央値は 1.03〜1.12、デスクトップの 12100 は 1.047 [実測](`x86-ng-cause-2026-11-14.md` §1.3)。
- これらは IPC ではなく実クロックの問題で、IPC 項では計算しない。「クロック依存の IPC の低下」(DRAM 遅延のサイクル数 ∝ f)はモデルにすでにあり、クロックが低い機体ではむしろ IPC が少し上がる向きに働く。

### 3.4 読み取り

- **DRAM 遅延という IPC 項で、モバイルの ST の過大のうち「モデルと最良条件の機体の差」はほぼ説明できる**。予測 ÷ P90 は S2st で -4.7〜+2.6%(S0 は -2.1〜+5.6%)。特に AMD の Zen 4・Zen 5 モバイル(`mobile-st-cause` の「AMD のモバイル固有の残り +6.7%」)は、DRAM 遅延でおおむね消える(HX 370 +0.6、350 -0.2、7840HS +1.0)。
- **残りの +5〜+12%(中央値と P90 の差)は IPC では説明できない**。同じ SKU の中で ST が P10〜P90 で 1.5〜2 倍に広がり、5800U では投稿の 72% が最大ブーストに届いていない。これはクロックの問題で、IPC 項を大きくして合わせると(K: mpkiL3 × 3)、ST は合っても u・σ が崩れて MT が ng 63 件になる。**IPC 項で一律 0.90 の代わりはできない**。
- 種別の遅延表(S1)では、デスクトップの DDR5 とノートの DDR5 が同じ 90ns になり、Zen 4・Zen 5 のモバイル(基準 DDR5-5600)の差が出ない。遅延は「種別」ではなく「プラットフォーム」で持つ必要がある。
- MT にも入れる(S2)と、c(0.412。モバイル 11 件の MT から決めた値)が遅延なしの前提なので、LPDDR の SKU の MT が一律に 5〜10 ポイント下がる(LNL -11.8%、185H -10.0%、PTL -9〜-12%)。MT に入れるなら c の再校正が要る(未試算)。

## 4. 提案(IPC 項のどこをどう直すか。実装はユーザー判断)

### 4.1 推奨: プラットフォームの DRAM 遅延を ST の dramNs に使う

| 項目 | 内容 |

### 4.3 提案しないもの

- `mpkiL3`・`mpkiL2` を大きくして L3・DRAM の効きを強める: mpki は校正前の仮の値で、変える根拠は Zen 3 の 1 組だけ。MT が大きく崩れる(K: ng 63)。
- モバイルの uarch ごとに u を別に持つ・係数を掛ける: 公開値に合わせるだけの係数になる。
- `memory.js` の種別の遅延表を絶対値で使う(S1): プラットフォームの差を表せず、効果がほとんど無い。
- 実クロックの低下を IPC として入れる: IPC ではない(§2.3)。

## 5. 直せない残り

| SKU | S2st の ST | 残りの理由 |
|---|---|---|
| Core Ultra 9 285H | +11.5%(ng) | 母集団(P90 ÷ 中央値 1.087)。P90 と比べた残り +2.6% は、285H の DRAM 遅延が未取得(155H の代用)なので確定できない。Arrow Lake-H の L3 遅延も未取得 |
| Ryzen 7 5800U | +14.4%(ng) | DRAM 遅延が未取得(変えていない)。残りは投稿の 72% が 4.4GHz に届かないこと(クロック)。4.4GHz に届いた投稿とは +1.2% |
| i7-14700HX | +11.1%(ng) | HX はデスクトップと同じダイで、IPC 項の差の出典がない。予測は P90 と +2.4% |
| Ryzen 7 7735HS | +10.6%(ng。境) | DRAM 遅延は 7840HS の代用。P90 と比べると +2.3%。Zen 3 の代表 5800X の公称超えのクロック(約 3 ポイント。`5800u-st-cause` §3.2)も残る |
| その他のモバイル(+3〜+9%) | ok | 母集団の差(中央値は P90 の 0.89〜0.97 倍) |

**まとめ**: IPC 項で計算できるのは、モバイルのメモリ遅延による 1.6〜3.8% の低下で、これは「モデルと最良条件の機体の差」をほぼ埋める。「Windows 投稿の中央値」までの残り(+5〜+12%)は、投稿機の ST のクロックの差で、IPC では計算できない。この残りを予測に入れるには、IPC 項ではなく「公開値の条件での実効クロック」(一律 0.90 の案、またはその代わりの表示上の注記)が必要になる。どちらにするかはユーザー判断。

## 6. 未取得・限界

- DRAM 遅延: 285H(Arrow Lake-H)、Panther Lake、Kraken 350、7735HS(Rembrandt-R)、5800U(Cezanne の絶対値)、Raptor の HX(SO-DIMM)、Zen 5 デスクトップの DDR5-5600、265K の DDR5-6400。AnandTech の 5950X の 78.8 ns と 5980HS の記述は、検索の要約だけで原ページは読めなかった(接続拒否・リダイレクト)。

- Zen 5 モバイルの FP 幅(256bit)が GB7 の ST に効くかの出典は未取得。
- MT に遅延を入れたときの c の再校正は試算していない。
- 試算の uCal の再計算は標本・除外ルールを据え置き、Redwood Cove の参考 SKU は 185H の構成のクロックと L3 だけを変えた仮の構成で計算した(既存の uCal と同じ方式)。
