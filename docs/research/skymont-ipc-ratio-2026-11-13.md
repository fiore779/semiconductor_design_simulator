# Skymont(Arrow Lake の E コア)の u を Lion Cove との IPC 比から決める案の検証(2026-11-13)

- 前提: `hx-mt-cause-analysis-2026-11-13.md`(6cd207f の後。σ=0.03306、γ=0.30、c=0.411、Lion Cove u=102.131、x86 ISA 平均 u=109.180、ng 33/158)。
- ユーザー提案: 「Skymont の IPC は Lion Cove の 80〜90% くらいなので、そこからクロック差を考慮すればスコアが出るのでは」。
- 方法: `tests/helpers.js` と同じ読み込みで `E.makeContext()` を作り、`perf.stScore` / `mtScore` に渡す u だけを差し替えて全プリセットを評価した(mobile-pc は現行の連続式 c·W^0.15)。σ を固定した場合と、`calibrateMt` で σ を決め直し、さらに連続式の c も標本 11 件で決め直した場合の両方を出した。**コード・データ・設計書・git は変更していない(試算のみ)**。使い捨てスクリプトは scratchpad の `sk0.js`〜`sk2.js`(結果は `sk2.out`)。
- 区分: [公表]=メーカー発表、[実測]=測定値そのもの、[二次]=報道・フォーラムの記述、[推定]=本メモでの計算。取得日はすべて 2026-11-13。

## 0. 結論(要約)

1. **モデルの u は IPC そのものではない**(確認済み)。1 コアの値は `u × ipc_model × f` で、ipc_model は uarch 記録(幅・ROB・L2・遅延)から計算する構造上の IPC。Lion Cove と Skymont では ipc_model がすでに違い、同じ条件(265K の L3、4.6GHz、1 スレッド)で **Skymont ÷ Lion Cove = 0.845**(MT の条件では 0.829)。このため「u_E = r × u(Lion Cove)」とすると、実際の 1 クロックあたりの比は **r ではなく約 0.845r** になる。
2. **出典つきの 1 クロックあたりの比は 0.86〜0.88(測定)、0.94(Intel 発表 2 つの組み合わせ)**。ユーザーの「80〜90%」と合っている。
   - [実測] ComputerBase(Cinebench 2024 MT、4.0GHz 固定): Skymont ≈ Lion Cove の **0.876**(1P+16E の結果から P 1 個分を引いた値。計算は [推定])。
   - [実測] David Huang の Geekbench 5.5.1(Linux、265K、P のみ / E のみ): **0.875**(クロック P 5.5・E 4.6 はフォーラムの記述 [二次]。P を 5.4 とすると 0.859)。
   - [公表] Intel: Skymont は Raptor Cove より IPC +2%(Lunar Lake の発表。L3・リング接続の条件)、Lion Cove は Raptor Cove より +9%(Arrow Lake の発表)。組み合わせると **1.02/1.09 = 0.936**(発表の条件が違う 2 つの数字を割った [推定])。
3. **提案を「物理的な IPC 比」として正しく入れる(B: u_E = r × u_LC ÷ 0.845)と、効果は小さい**。測定の r=0.875 なら u_E=105.7(現状の 109.18 から -3%)。285K は +10.8 → +8.6%(ok)になるが、275HX +13.7%・285H +15.4% は ng のまま(ng 33 → 32)。
4. **u の比として文字どおり入れる(A: u_E = r × u_LC)と、r=0.80〜0.90 で ng 33 → 30**(285K・275HX・285H が ok。ok→ng は 0 件。リング接続の E だけに当て、σ を固定した場合)。r=0.90 の u_E=91.9 は、前回の 285K の MT から逆算した 91.7 とほぼ同じ。**ただし A の r=0.90 は、1 クロックあたりの比に直すと 0.76 で、測定の 0.86〜0.88 より 13% 低い**。つまり A で合うのは「IPC 比から決めたから」ではなく、「285K に合わせた値と同じだから」(推測。数値は確認済み)。
5. **推奨(ユーザー判断)**: 当てるのはリング接続の E コア(種別 E の Skymont: 285K・265K・275HX・285H)だけ。LP-E(Lunar Lake の 4 個、285H の 2 個)には当てない(当てると LNL 3 件が ok→ng)。σ の代表に 265K が入らない形で実装する(入ると σ が動き、7950X などが ok→ng)。値は次のどちらかを選ぶ必要がある。
   - **出典を優先する場合**: B、r=0.875(測定)。ng 32。275HX・285H の残りは E コアの IPC 以外の要因として未解決のまま残る。
   - **誤差を優先する場合**: A、r=0.90(u 比)。ng 30。**「IPC 比 90%」とは書かず、「Lion Cove の u に対する比 0.90。285K・265K の MT に合う [推定・校正値]。1 クロックあたりの比に直すと 0.76 で、測定の 0.86〜0.88 より低い」と書く必要がある**。
   - 本メモの見立ては後者(A 0.90)が実用的。ただし残りの約 13% が何か(全コア負荷時の E のクロック、24 スレッドの η、リングや L3 の帯域の競合、GB7 の MT 負荷の性質)は分けられていない(推測)。

## 3. 試算

### 3.1 2 つの入れ方

- **A(u の比として文字どおり)**: u_E = r × 102.131。1 クロックあたりの比は約 0.845r。

### 3.3 σ を決め直す場合(Skymont に uCal などで uarch 専用の u を入れたとき)

`calibrateMt` は「全コアが uarch 専用の補正を持つ代表」だけで σ を決める。いま 265K(Lion Cove の代表、calib:true)は E が ISA 平均を借りているので σ の代表に入っていない。**Skymont に uarch 専用の u(uCal や新しい uarch 記録)を入れると、265K が 5 件目の σ の代表になり、σ が動く**(確認済み)。

| A 0.875 | 0.03184 | 0.405 | +0.2 | -4.1 | +3.5 | +7.2 | 32 | 7950X(+11.4)、8200 |

| B 0.875 | 0.03372 | 0.416 | +7.7 | +2.3 | +13.8 | +15.8 | 32 | EPYC 7401(-9.4 → -10.5)、865 |

- σ を決め直すと、AMD・スマホ SoC など Arrow Lake と関係ない SKU が 1〜4 ポイント動き、ok→ng が出る。**σ の代表は「出典つきの u を持つコアだけ」というこれまでの方針から見ても、MT から逆算した値で決めた Skymont の u を σ の代表に入れるのは循環になる**(推測)。実装するなら、σ の代表の判定では Skymont を「uarch 専用ではない」扱いにする必要がある(例: 新しい corrSource 'ratio' を作り、`calibrateMt` の `every(corrSource === 'uarch')` に通さない)。
- B 0.85 で σ を決め直す案は ng 30 だが、285K を除く Arrow Lake は直らず(275HX +11.9、285H +14.2)、12100・780G の ng→ok は境界(10.1 → 9.9)の偶然。

### 3.4 前回の逆算値(285K 91.7、265K 99.8)との整合

| 逆算 | u | A に直した r(u ÷ 102.131) | B に直した r(A ÷ 1.1827) |
|---|---|---|---|
| 285K の MT 誤差 0 | 91.70 | **0.898** | 0.759 |
| 265K の MT 誤差 0 | 99.84 | 0.978 | 0.827 |
| 2 件の中央値(前回の H3c) | 95.77 | 0.938 | 0.793 |

- A の r=0.90 は 285K の逆算値と同じ。A の r=0.936(Intel の発表の組み合わせ)は前回の H3c(95.77)とほぼ同じで、結果も同じ(ng 31、285H +10.3%)。
- 1 クロックあたりの比(B)に直すと、285K・265K が求める比は **0.76〜0.83**。測定(0.86〜0.88)より 5〜13% 低い。**MT の過大の一部は E コアの IPC では説明できない**(数値は確認済み、解釈は推測)。候補: GB7 の MT 負荷での E のクロックが 4.6GHz より低い(TechPowerUp の「E は常に 4.6GHz」は BIOS の設定で、GB7 の実行中の値は未取得)、24 スレッドの η(σ は AMD の代表で決めた値)、E のクラスタ(4 コアで L2 4MB を共有)やリングの帯域の競合。
- 285K と 265K で必要な r が違う(A で 0.898 と 0.978)。1 つの r で両方を ±0 にはできない。A 0.90 では 285K +0.1・265K -4.2 で、x86 デスクトップの MT MAE が最小(5.43)。

## 4. 結論と推奨

### 4.1 提案の妥当性

- **考え方(E の性能を P との比とクロックの差で決める)は、出典の数字と合う**(確認済み): 測定の 1 クロックあたりの比は 0.86〜0.88 で、「80〜90%」の範囲に入る。モデルはすでにコア別のクロック(285K の P 5.4・E 4.6 など)を持っているので、クロックの差は自動で入る。
- **ただし、現状のモデルはすでに「約 90%」になっている**(ISA 平均の u と構造上の IPC の比 0.845 を掛けると 0.904)。比を測定の 0.875 に下げても、E の寄与は 3% しか下がらない。**IPC 比だけでは 275HX・285H の過大は直らない**(B 0.875 で +13.7%・+15.4%)。
- 「u_E = r × u(Lion Cove)」と文字どおり入れれば r=0.80〜0.90 で ng 30 になるが、それは u と IPC を取り違えた結果、たまたま 285K の逆算値に近い値になったもの(推測。数値は確認済み)。

### 4.2 推奨する実装(実装はしない。ユーザー判断)

1. **当てる範囲: 種別 E の Skymont だけ**(285K・265K・275HX・285H の E)。LP-E(Lunar Lake 3 件、285H の 2 個)は ISA 平均のまま。Darkmont(Panther Lake)・Crestmont は対象外(Panther Lake の MT は -2〜0% で合っている)。
2. **方法**: `data/uarch.js` に「Skymont(Arrow Lake のリング接続 E)」の記録を分け、プリセットの E の uarch をそれに替える。u は Lion Cove の u との比で持つ(例: `uRatio: { of: 'Lion Cove', r }`)。こうすると、Lion Cove の u が代表の取り直しで動いたときに一緒に動く。**σ の代表の判定では uarch 専用として扱わない**(§3.3)。確度は「低」のまま。
3. **r の値(どちらか)**:
   - (a) **出典を優先**: B、1 クロックあたりの比 0.875(S1・S2 の測定)。u_E=105.7。ng 33 → 32(285K のみ ok)。
   - (b) **誤差を優先(本メモの推奨)**: A、u の比 0.90。u_E=91.9。ng 33 → 30(285K +0.1、265K -4.2、275HX +4.8、285H +8.5)、ok→ng 0 件、x86 モバイルの MT MAE 7.14 → 6.24、デスクトップ 5.87 → 5.43。**記録には「IPC 比」と書かず、「Lion Cove の u に対する比 0.90。285K・265K の MT に合う [推定・校正値]。1 クロックあたりの比に直すと 0.76 で、測定の 0.86〜0.88 より低い(差は E の IPC 以外の要因で、未特定)」と書く**。
4. **副作用**(確認済み): (b) では、Skymont を使わない SKU は全件不変、ST も全件不変。285H は +8.5% で ok になるが、ST が +16.8% の ng のまま(モバイルの ST の不足は別の課題。前回 §5)。275HX の MT/ST の残差は小さくなる。265K は Lion Cove の代表なので ST は 0.0% のまま。
5. **先に取れると良い出典**: GB7 の P のみ・E のみの ST(1 クロックあたりの比を GB7 で直接測る)。GB7 の MT 実行中の E のクロック。これがあれば (a) と (b) の差(約 13%)の内訳を分けられる。
